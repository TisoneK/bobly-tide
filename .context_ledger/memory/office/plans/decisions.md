## ADR-1: Client platform is Flutter (2026-10-24)
- **Status:** accepted
- **Context:** The product is mobile-first for Kenya (M-Pesa, Android-dominant). A client platform had to be fixed before any build work.
- **Decision:** Build the member app in Flutter (Dart), one codebase for Android + iOS. Android is the pilot priority.
- **Consequences:** Backend stays a separate service (not locked — see build spec §13-D1). Flutter state management proposed as Riverpod (D3). Future agents target Flutter; do not introduce a second client framework without a superseding ADR.

## ADR-2: MVP is the closed-pilot slice — Daily package only (2026-10-24)
- **Status:** accepted
- **Context:** The product spec defines five packages and a four-phase launch. Building all of it before proving the hourly mechanic is wasteful and risky with real money.
- **Decision:** v1 = Launch Phase 1 only: the Daily (24-member) package, 3–5 invited groups, with wallet, M-Pesa top-up/withdraw, the hourly engine, fixed turn order, security hold, and defaults. All other packages and growth surfaces are deferred.
- **Consequences:** Build and tests focus on one package type; the data model still generalises to N-member packages so later packages need no rewrite. Scope creep past the pilot slice is rejected until the pilot proves the mechanic.

## ADR-4: Backend is Node + TypeScript + PostgreSQL (2026-10-24)
- **Status:** accepted
- **Context:** Build spec §13-D1 left the backend language open (Dart / Node-NestJS / Python-FastAPI). The user locked the §13 defaults and asked to start the build, so one had to be chosen. The money ledger and hourly settlement need exact decimal math, serialisable transactions, and a reliable job runner — all three languages qualify; the deciding signal was the local toolchain (modern Node v24.17.0 present; system Python only 3.9.6).
- **Decision:** Backend in Node + TypeScript with PostgreSQL. The pilot skeleton is framework-light (pure domain engine + tests) with `decimal.js` for exact money; NestJS is added at the HTTP/API-layer step, not before. The remaining §13 defaults (D2 hosting TBD, D3 Riverpod, D4 fonts, D5 accent colors, D6 SMS provider, D7 ops console read-mostly, D8 business placeholders) are locked as proposed.
- **Consequences:** Money columns use exact decimal (`NUMERIC(14,4)` in Postgres, `decimal.js` in code) — never floats. The hourly tick is server-authoritative and idempotent per `(group, hour)`. Future agents build on TypeScript + Postgres; a different backend language needs a superseding ADR.

## ADR-5: Security-hold model (2026-10-24)
- **Status:** accepted
- **Context:** Product spec §8 requires a security hold that covers the contributions a member still owes, sized so early turn positions hold more than late ones, drawn on shortfall and released as the cycle runs. An exact sizing formula and a ledger representation had to be chosen.
- **Decision:** Hold for turn position p = `(N − p) × contribution` — the post-payout exposure (contributions owed for the hours after a member collects). The hold is a separate per-member internal account (`hold:<membershipId>`), funded by moving money out of the spendable wallet at group start; a wallet balance therefore stays "spendable money" and the hold account is "locked collateral", and the two sum to the member's total. On a wallet shortfall the engine unlocks the gap from the hold (a `hold_release` pair) before the `hourly_debit`, so pots stay whole and money is conserved. Leftover collateral is returned at cycle end / on default; a defaulted member's unreceived turn is forfeited automatically because the engine only pays the current active holder of a position.
- **Consequences:** Incremental per-hour release of collateral is deliberately NOT implemented — final balances are already correct (draw-on-shortfall + end-of-cycle release), so it is only a mid-cycle wallet/hold split nicety, logged as a later refinement. Grace-period timing and SMS warnings (§8.2) belong to the scheduler/notifications layer, not the engine. Postgres `UNIQUE(group_id, join_order)` means a real replacement relinks/reuses the vacated row rather than inserting a duplicate position (the in-memory fixture allows the duplicate). Future agents keep the sizing formula and the separate-hold-account model unless a superseding ADR changes them.

## ADR-6: Postgres persistence via a load-run-persist unit of work (2026-10-24)
- **Status:** accepted
- **Context:** The pure money engine is synchronous (operates on an in-memory `LedgerRepo`); Node cannot do synchronous DB I/O. Running the engine on a real database meant either making the whole engine async (destabilising 23 passing tests) or bridging sync↔async at the persistence boundary.
- **Decision:** Keep the engine pure and synchronous. `PgLedgerRepo` (`src/repo/pg.ts`) is the durable append-only store (async). A unit of work (`src/pg-settlement.ts` → `withLedger` / `settleHourOnPg`) loads the accounts a settlement touches into an in-memory snapshot, runs the pure engine against it, and writes back only the new entries in one transaction. Idempotency comes from the snapshot (a re-run sees the prior settlement → `already-settled`), with the ledger's `UNIQUE(idempotency_key)` as the concurrency backstop. The ledger is keyed by an opaque TEXT `account_id` (member wallet id, `PLATFORM`, or `hold:<membershipId>`) rather than a UUID wallet FK, so the engine's account model maps straight onto it. Migrations are plain `db/migrations/*.sql` applied by `runMigrations`. `balanceOf` sums with decimal.js (exact at any scale, driver-independent).
- **Consequences:** The money engine never depends on the DB and stays unit-testable; persistence is a separable concern. Integration tests run against `pg-mem` (in-process, no Docker) and the same code targets real Postgres. The snapshot loads a group's full account history each settlement — fine at pilot scale; a materialised balance is the scale-up path. Future agents extend persistence through the unit of work rather than making the engine async, unless a superseding ADR changes it.

## ADR-7: NestJS HTTP API + interval scheduler (2026-10-24)
- **Status:** accepted
- **Context:** The engine/persistence needed a service layer: an HTTP API over groups/wallets and a scheduler to drive settlement hourly. Build spec §13-D1 locked NestJS. But the run/test toolchain (tsx + vitest, both esbuild) does NOT emit TypeScript decorator metadata, which NestJS's default reflection-based DI relies on; and `@nestjs/schedule` adds another decorator-metadata-scanning dependency.
- **Decision:** Use NestJS with **explicit token-based DI only** — every injected dependency carries `@Inject(TOKEN)`, never relying on constructor type reflection (tokens in `src/api/tokens.ts`; providers wired via `AppModule.forRoot({pool, pkg, scheduler})` with `useValue`/`useFactory`). Decorators are enabled in tsconfig (`experimentalDecorators`, `useDefineForClassFields:false`); a boot spike test (`test/api-boot.test.ts`) guards that this keeps working. The scheduler is a plain `SchedulerService` using `setInterval` (not `@nestjs/schedule`): on each tick it lists active groups and calls `settleDueHours` (`src/scheduler.ts`, framework-free and unit-tested), which settles every due hour idempotently and, on the final hour, releases holds and completes the group. The "hour" is a configurable `HOUR_MS` so pilots/tests run accelerated time. The wallet top-up endpoint is an internal/dev credit standing in for M-Pesa until Daraja (§7).
- **Consequences:** NestJS runs under the esbuild toolchain without a separate SWC/tsc build; the trade-off is the `@Inject` boilerplate, enforced by convention + the spike test. Integration is proven end-to-end against pg-mem (API e2e + scheduler suites). `@nestjs/platform-express` pulls in `multer` transitively (unused — no file uploads); it is pinned to patched 2.5.0 via a package.json `overrides` entry to keep prod-dep audit clean. Future agents keep token DI and drive settlement through `settleDueHours`; swapping in `@nestjs/schedule` or SWC would need a superseding ADR.

## ADR-8: M-Pesa (Daraja) money movement — callback-as-truth (2026-10-25)
- **Status:** accepted
- **Context:** The wallet needed real money in (STK push) and out (B2C) via M-Pesa Daraja (build spec §7), replacing the internal dev top-up. Daraja confirms asynchronously via callbacks, so the design had to decide exactly when the wallet moves — and keep it correct against replayed/duplicate callbacks and against double-spend between a withdrawal request and its result.
- **Decision:** The wallet is the source of truth and moves on the **confirming callback**. Top-up: `initiateTopup` calls STK push and records a pending `mpesa_txn`; the wallet is credited only when the STK callback reports success, keyed on the Daraja `CheckoutRequestID` (idempotent — a replayed callback never double-credits; guarded by `hasEntryWithKey`). Withdrawal: funds are **reserved** (debited) at request time keyed on a local ref, so they cannot be double-spent while the B2C is in flight; a success callback lets the debit stand, a failure callback (or a failure of the B2C call itself) reverses it with a keyed refund. Code depends on a `DarajaClient` interface: `FakeDarajaClient` for tests + credential-less local dev (no real calls; callbacks are simulated by POSTing the callback endpoints), `HttpDarajaClient` for sandbox/production. `main.ts` selects Http when `DARAJA_CONSUMER_KEY` is set, else the fake. All credentials come from env (`.env.example` documents them); no secret values in tracked files, `.env` gitignored.
- **Consequences:** Settlement correctness is preserved — every wallet move reuses the append-only ledger + unit of work, so top-ups/withdrawals/refunds are exact and idempotent like the engine's entries. The reservation model means a wallet balance already reflects an in-flight withdrawal (pending `mpesa_txn` records the Daraja state). `HttpDarajaClient` is written to the Daraja spec but not unit-tested (the suite uses the fake); it needs sandbox verification before go-live. Callbacks are currently unauthenticated endpoints — before production they need Daraja source validation / a shared secret. The ledger credits the amount we initiated, not the callback's amount; a reconciliation step is a later refinement. Future agents move money only through the callback path and keep it idempotent.

## ADR-9: Phone + OTP auth with HS256 session tokens (2026-10-25)
- **Status:** accepted
- **Context:** The API needed authentication (build spec §8): request/verify a one-time code, issue a session token, and protect the group/wallet routes. Two sub-decisions mattered — the token format (and whether to add a JWT dependency) and how to do DI-based guards under the esbuild toolchain that emits no decorator metadata (same constraint as ADR-7).
- **Decision:** `AuthService` (`src/auth/`) issues a 6-digit code via an injected `SmsSender` (interface; `FakeSmsSender` for tests/dev, real provider later), stores it **hashed** in `otp_code` (migration 0002) with a short TTL, single-use (consumed), and an attempt lock. Verify maps the phone to a stable `app_user` (find-or-create) and returns a minimal **HS256 JWT** implemented in `src/auth/jwt.ts` with `node:crypto` — no `jsonwebtoken` dependency. `AuthGuard` (token-DI, `@Inject(AUTH_CONFIG)`) enforces a Bearer token on `GroupsController`, `WalletsController`, and the M-Pesa top-up/withdraw routes; `/auth/*` and the Daraja callbacks stay public. `AUTH_JWT_SECRET` and TTLs come from env (`main.ts` generates an ephemeral secret with a warning if unset — dev only); no secret values in code.
- **Consequences:** No new runtime dependency for tokens; the JWT is intentionally minimal (HS256, exp check) and not a full JWKS/refresh-token system. The guard **authenticates only** — it does not yet authorize per-resource ownership (a valid session can act on any wallet/group), and a group join still creates its own throwaway user rather than tying membership to the authed user; both are logged follow-ups for the member-journey work. Callbacks remain unauthenticated (see ADR-8). Future agents keep token-DI for guards and extend authz on top of the guard rather than replacing it, unless a superseding ADR changes the token scheme.

## ADR-10: Flutter member client (2026-10-25)
- **Status:** accepted
- **Context:** The pilot member app (build spec §14 step 4) sits on the backend API. Decisions: state management (D3 locked Riverpod), HTTP layer, how the client is structured, and how the member reaches a group given the current API surface. No Flutter SDK is available in the build environment, so it cannot be compiled or run here.
- **Decision:** Flutter + `flutter_riverpod` (D3) + the `http` package, under `app/`. Screens: sign-in → OTP → home (Daily package + join), group (queue when filling / turn order when active), wallet (balance + receipts with M-Pesa top-up/withdraw sheets). An `ApiClient` is rebuilt whenever the session token changes (token-scoped provider); the session is held **in memory** for the pilot. Theme leads with deep sea blue per ADR-3 / build spec §9. Because the backend has no "find a filling group for a package" endpoint and no "my groups" lookup, the client **joins by invite code (the group id)** and remembers the membership locally — matching the invite-only pilot (build spec Phase 2). Platform folders (android/ios) are NOT committed; `flutter create .` regenerates them.
- **Consequences:** The app is authored, not verified — no `flutter analyze`/`test` ran here; it needs a Flutter machine to build and a device/emulator to confirm (logged, and noted in `app/README.md` + the build-spec status). The in-memory token and invite-code join are explicit pilot shortcuts tied to the same member-journey follow-ups as ADR-9 (secure-storage token; a package→group join endpoint that ties membership to the authed user). `withOpacity` is used over `withValues` to keep the Flutter ≥3.22 floor. Future agents regenerate platform folders rather than committing them, and keep the API-client/model layer in sync with the backend JSON.

## ADR-11: Member-journey hardening — package join + per-resource ownership (2026-10-25)
- **Status:** accepted
- **Context:** ADR-9/ADR-10 left two follow-ups: a group join created a throwaway user instead of tying membership to the authenticated caller, the client reached a group by invite code because there was no package→group allocation endpoint, and the API authenticated but did not authorize per-resource (a valid session could act on any wallet/group, and the group view exposed every member's balance).
- **Decision:** Joins tie to the authenticated user. `GroupStore.createMembershipForUser(groupId, userId, pkg)` replaces the user-minting join; `joinPackage(userId, pkg)` allocates the earliest filling group with room the user isn't already in (creating one if none) — exposed as `POST /packages/daily/join`, and `POST /groups/:id/join` now also uses the caller. A `@CurrentUser()` param decorator (via `createParamDecorator`, metadata-free like the guards) reads the claims AuthGuard set. Ownership: `requireWalletOwner` gates wallet GET and M-Pesa top-up/withdraw (403 whether the wallet is another's or absent, so ids don't leak); group start/settle-due/GET require membership (`GroupStore.isMember`); and the group view is redacted to the caller's own position+balance plus other members' position/state only (no other balances). `toHttp` passes `HttpException`s (e.g. Forbidden) through unchanged. A test/seed-only `joinGroupAsNewUser` keeps the non-auth suites (scheduler, mpesa) simple.
- **Consequences:** The Flutter client drops the invite-code workaround — home calls `joinDaily()` and the group view consumes `yourPosition`/`yourBalance` + redacted members (models + screens updated). `UNIQUE(group_id, user_id)` means one membership per user per group; a repeat package-join lands the user in a different group (per-user group limits, product spec §8.5, still a follow-up). Operational endpoints (`POST /groups` create) stay authenticated-only — there is no admin role yet, so start/settle-due are gated by group membership rather than a role (admin-role separation is a follow-up). Remaining follow-ups: secure-storage token, Daraja sandbox verification + callback source validation, and on-device verification of the app.

## ADR-12: Tiered KYC verification gating (2026-10-25)
- **Status:** accepted
- **Context:** Product/build spec §6 require ID verification before a member handles money. The user asked that an account be usable for browsing after phone sign-in, but that joining unfilled groups and any financial transaction be blocked until the member verifies email, ID, face and address. No real KYC/email vendor is available in the build environment.
- **Decision:** A `verification` table holds one row per (user, kind ∈ email|id|face|address) with a status (unverified|pending|verified|rejected); `email_code` mirrors the OTP table for self-service email confirmation (hashed, short-lived, single-use). `VerificationService` (`src/verification/`) exposes `startEmail`/`confirmEmail` (code via an `EmailSender` interface), `submit` for id/face/address (through a `KycProvider` interface), `status`, and `requireVerified`. The required set is configurable (`VERIFICATION_REQUIRED`, default all four). Gating: `requireVerified(userId)` is called at the top of `POST /packages/daily/join`, `POST /groups/:id/join`, and M-Pesa top-up/withdraw, throwing `VerificationRequiredError` → 403 listing the missing items. Providers follow the Fake/real pattern (like SmsSender/Daraja): `FakeEmailSender`/`FakeKycProvider` for tests and dev; `FakeKycProvider(autoApprove)` is driven by `KYC_AUTO_APPROVE` (default false → submissions stay `pending`, since auto-approving identity in production is unsafe).
- **Consequences:** Browsing (package list, your own status) needs only a phone session; money and joining need full KYC. With no real vendor, id/face/address stay pending unless auto-approve is on, so a real pilot must wire a provider (e.g. Smile ID) and an ops review/callback to resolve pending submissions — logged as a follow-up (no admin role yet). The email-code pepper reuses `AUTH_JWT_SECRET`. The Flutter client still needs a verification screen before it can join (done in the client pass). Future agents gate new money/join routes with `requireVerified` and add KYC kinds via the same table + provider.

## ADR-13: Payout order = security-posting order (FCFS) + turn countdown (2026-10-25)
- **Status:** accepted · supersedes the join-order turn assignment in ADR-2's engine
- **Context:** The user specified that once a group is full, members are paid in the order they posted their security — first-come-first-served — not join order; and the client should count down to each member's turn. The engine previously paid by `join_order`.
- **Decision:** Membership gains `turn_position` (nullable until secured) and `secured_at` (migration 0004); `join_order` stays as the join sequence for the queue. A new `POST /groups/:id/secure` assigns `turn_position = (securedCount)+1` in secure order and locks that position's hold `(N − position) × contribution` from the member's wallet via the unit of work (so securing earlier buys an earlier turn **and** a larger hold, since an earlier payee owes more afterwards — required for the pot to stay whole). The group auto-activates (`state=active`, `start_at=now`) when the last member secures; the old all-at-once `POST /groups/:id/start` is removed. The engine pays `turn_position` p at hour p−1 (`settleHour` finds the holder by `turnPosition`; holds size by `turnPosition`). `GET /groups/:id` returns `yourTurnAt = start_at + (position−1)·hourMs` for the client countdown, plus `joined`/`securedCount` and per-member `turnPosition`. Securing is gated by verification + group membership. Seeds/tests set `turnPosition = joinOrder` so existing money suites are unchanged.
- **Consequences:** The whole pot-conservation model still holds — only the position→member mapping changed. A group can stall if a joined member never secures (no auto-timeout yet — a pilot-ops follow-up). Securing while the group is still filling is allowed (claim your turn early). The Flutter group screen gained a "post security" action and a live countdown; its `GroupView` model now carries nullable `yourPosition`/`turnPosition` + `yourTurnAt`. Vitest `testTimeout` raised to 30s (the pg-mem full-cycle suite is legitimately slow). Future agents keep turn order keyed on `turn_position`.
